# 1. What This Is

VoucherSense AI is an AI-powered receipt processing application, built as an AI engineering assessment. A user uploads one or more receipt photographs or PDFs; a background worker extracts structured expense data from each with an AI model; once that extraction is validated, the user can request a one-time plain-language summary of it.

This repository is an **AI Integration Slice** — a single, complete flow rather than a general accounting platform:

```
Register -> Login -> Upload -> Jobs -> Results -> (one-time) Summary
```

## The problem it solves

Manually logging expenses from paper receipts is slow and error-prone. The slice shows how a vision-capable AI model can:

1. Turn a raw receipt image/PDF into structured, validated expense data (merchant, date, total, category, line items), and
2. Turn that validated data into a short natural-language summary — without the model silently "re-reading" or overriding the extracted values.

The value is not the AI call itself. It is the machinery around it: file validation, background job processing, structured-output validation, retries, timeouts, honest failure recording, rate limiting, and per-user ownership — everything that separates a demo from something you could argue about line-by-line in review.

## Scope of the implemented flow

- **Input:** single receipt images (JPEG/PNG) and PDFs, uploaded in batches of up to 50 files per request.
- **Role 1 — Extractor:** reads the receipt and returns a structured JSON extraction.
- **Role 2 — Analyst:** reads only the validated extraction JSON and returns a summary.
- **Auth:** a minimal account system (register, login, logout, sessions, route protection, ownership checks).
- **Out of scope:** anything in [Section 7](#7-what-this-slice-does-not-handle).

## AI provider

Google Gemini is the only AI provider, used through the official `@google/genai` npm SDK (`GEMINI_API_KEY`, model set by `GEMINI_MODEL`). **One model serves both roles** — the roles differ only by system prompt and JSON schema, which keeps the architecture simple and the evidence readable. Application code never imports the SDK directly; all calls go through one wrapper, `lib/ai/geminiClient.ts`.

# 2. How To Run It

## Prerequisites

| Dependency | Requirement |
|---|---|
| Node.js | Current stable / LTS (AGENTS.md §5). No `engines` pin in `package.json`; verified locally on Node v26.2.0. |
| PostgreSQL | A running PostgreSQL instance (local or remote) — the app uses Postgres as the database *and* as the job queue. |

| Google Gemini API key | A valid key for a vision-capable Gemini model (Role 1 needs image/PDF understanding). |

```bash
npm install
```

Copy the example file and fill in the values:

### Local-timeout note (this machine)

During local testing, single Gemini calls were observed taking longer than the 30 s default. `.env` on this machine currently overrides the code defaults:

- `AI_TIMEOUT_MS=90000`
- `STALE_JOB_TIMEOUT_MS=180000` (2 × 90 s, per the "2× the AI timeout" rule in `config/index.ts`)

These are **local tuning values**, not code defaults — `.env.example` and the code defaults still say 30 s / 60 s. Confirm them against your network latency and any deployment platform's function timeout (an open decision, see [Section 6](#6-what-went-wrong)).

# 3. The Flow, Step By Step

## End-to-end user journey

1. **Register.** `POST /api/auth/register` validates a basic email shape and a minimum password length (8 characters), checks the email is not already taken, and stores a scrypt hash — never a plaintext password.
2. **Login.** `POST /api/auth/login` verifies the credentials and issues a signed, `httpOnly` session cookie (`vs_session`). The same generic 401 is returned for an unknown email or a wrong password, so an attacker cannot enumerate registered addresses.
3. **Protected upload screen.** Entering the app is gated; unauthenticated users are shown the auth screen. The upload screen is only reachable with a valid session.
4. **Select files.** The uploader accepts JPEG/PNG/PDF files, one or many per batch.
5. **Validate each file.** `lib/files/validateFile.ts` runs four fail-fast checks per file, and only per file — one bad file never blocks the rest of the batch:
   1. MIME type is in the allow-list (`image/jpeg`, `image/png`, `application/pdf`);
   2. size is within `MAX_UPLOAD_BYTES` and non-empty;
   3. images actually decode via `sharp` (catches fake extensions);
   4. PDFs start with the `%PDF-` magic bytes.
6. **Store valid files.** Only after validation passes is the buffer written through the storage abstraction (`lib/storage`) to a key like `receipts/2026/09/<id>.png`.
7. **Database stores the key, not the binary.** A `Receipt` row is created with `storageKey`, filename, MIME type, size, and the `batchId` — the file bytes never touch the database (see [Section 4](#4-the-data-model)).
8. **A background Job is created.** In the same transaction as the `Receipt`, exactly one `Job` row is created with status `pending`. The batch route returns the job ids immediately; the heavy lifting happens in the background.
9. **The worker claims the job.** `worker/claimJob.ts` runs `SELECT … FOR UPDATE SKIP LOCKED` inside a Postgres `UPDATE`, atomically flipping the oldest `pending` job to `processing` and stamping `claimedBy`/`claimedAt`. Two worker loops can never claim the same row.
10. **Role 1 extracts.** `worker/processJob.ts` reads the file from storage and calls `extractReceipt` via `lib/ai/geminiClient.ts` — the only module allowed to talk to the Gemini SDK. The image/PDF is sent inline; the structured JSON schema is sent alongside.
11. **Gemini returns structured output.** Each call has an enforced timeout and requests `responseMimeType: "application/json"` plus a Gemini-native `responseSchema`.
12. **The response is checked, then Zod-validated.** Truncation is detected from the provider's `finishReason` **before** any parsing. A non-truncated response is parsed and run through the Zod `ExtractionSchema` (item cap of 40, real calendar-date check, enum values, non-negative totals).
13. **Failures are recorded honestly.** Validation failures, truncation, timeouts, and provider errors each become a `JobAttempt` row with a distinct outcome (`valid` / `invalid_schema` / `truncated` / `timeout` / `provider_error`). Retryable classes (truncation, invalid schema) retry with the specific error fed back in the next prompt; timeout and provider error are terminal and mark the job `failed` with an honest `errorMessage`.
14. **Successful extraction is persisted.** Only a Zod-validated response creates an `ExtractionResult`; the job is then marked `done`. An HTTP 200 was never proof of success — passage through the Zod gate is.
15. **The user watches status.** The jobs screen polls `GET /api/jobs` and shows each file moving `pending → processing → done | failed` (including a confidence badge when done).
16. **The user opens the result.** The result screen (`/jobs/<id>`) shows the validated extraction: merchant, total, date, payment method, category, line items, and confidence note.
17. **One-time summary.** The result screen offers "Summarise expenses". `POST /api/results/<id>/summarize` is the single approved synchronous AI call in the app (Role 2).
18. **Role 2 sees only validated data.** `analyzeExpense` receives the validated `ExtractionResult` JSON — never the original receipt file or bytes.
19. **The summary is validated and stored.** The model's response must pass the Zod `SummarySchema` before a `Summary` row is written as `done`. Summarization is idempotent: a second request for the same result returns the existing summary without a new AI call.
20. **The user sees the summary.** The result screen renders the summary text and derived figures.

## Retry behaviour

- **Worker retries:** truncation and schema-invalid responses are retried up to `AI_MAX_RETRIES` (2) extra times. Every retry prompt includes the specific error/truncation detail from the previous attempt — identical retry prompts are forbidden by design.
- **Timeout / provider error:** terminal per PRD §4.2. The job lands in `failed` with an honest `errorMessage`; no silent retry hides the provider problem.
- **Manual retry:** `POST /api/jobs/<id>/retry` re-enqueues a job **only if** it is `failed`; anything else returns HTTP 409. `RETRY` counts against the upload rate-limit bucket. Retried jobs continue attempt numbering from the highest recorded attempt so the audit trail stays unambiguous.
- **Stale-job recovery (reaper):** every poll cycle, before claiming new work, `worker/reapStaleJobs.ts` requeues jobs stuck in `processing` longer than `STALE_JOB_TIMEOUT_MS` (if attempts remain) or fails them (if retries are exhausted). No job can sit in `processing` forever.

## Ownership checks

Every protected resource is resolved back to its `Receipt.userId`, derived from the signed session cookie — a client-supplied user id is never trusted. Accessing another user's job, result, or summary returns **HTTP 403**; unauthenticated requests return **401**. Confirmed live: user B got 403s on user A's job/result/retry/summarize/summary, and user B's own job list was empty.

## Rate limiting

Two independent per-user buckets (fixed window of 60 s, in-memory):
- **Upload** (`RATE_LIMIT_UPLOAD`, 10/min) — counts *requests*, not files; a 50-file batch costs one unit. `retry` also flows through this bucket.
- **Summarize** (`RATE_LIMIT_SUMMARIZE`, 20/min) — tracked separately.

A rejection is an explicit **HTTP 429** with a clear message — never a silent queue or drop. Confirmed live: upload 429 at the 11th request in a minute; summarize 429 at the 21st.

## Sessions & logout

- Login issues an `httpOnly`, `SameSite=Lax`, path-`/` cookie signed with HMAC-SHA256; it is `Secure` in production.
- Every protected route verifies the cookie signature and that the token's age is within `SESSION_MAX_AGE_SECONDS` (default 12 h).
- `DELETE /api/session` clears the cookie (logout); after it, protected routes reject again.
- Session expiry was confirmed live on a second instance with `SESSION_MAX_AGE_SECONDS=1`: an immediate request was authenticated, a request 4 s later was not.

# 4. The Data Model

Six Prisma models, matching PRD §2. The schema is PostgreSQL-only and lives in `prisma/schema.prisma`.

```
User
 ├─ id (cuid)
 ├─ email (unique, nullable — legacy demo rows have none)   [auth]
 ├─ passwordHash (scrypt hash, nullable)                    [auth]
 └─ receipts 1—* Receipt

Receipt
 ├─ id
 ├─ userId ──────────────────────────────► owns everything downstream
 ├─ storageKey        "receipts/2026/09/<id>.png"  (never the binary)
 ├─ originalFilename, mimeType, sizeBytes
 ├─ batchId           groups files submitted in one request
 └─ 0..1 Job

Job
 ├─ id, receiptId (one-to-one),
 ├─ status: pending | processing | done | failed
 ├─ attemptCount, errorMessage,
 ├─ claimedBy / claimedAt    (worker stamp while processing)
 ├─ attempts 1—* JobAttempt
 └─ 0..1 ExtractionResult

JobAttempt
 ├─ jobId, attemptNumber
 ├─ outcome: valid | invalid_schema | truncated | timeout | provider_error
 ├─ rawResponse (Text), validationError (Text|null)
 └─ createdAt

ExtractionResult
 ├─ id, jobId (unique)
 ├─ merchant, purchaseDate, currency, total
 ├─ paymentMethod, category            (enum values, validated at app layer)
 ├─ items (JSON — max 40 × {name, quantity, unit_price, line_total})
 ├─ confidenceNote
 └─ 0..1 Summary

Summary
 ├─ id, extractionResultId (unique)
 ├─ status: pending | done | failed
 ├─ attemptCount, errorMessage
 ├─ summaryText, totalSpent, currency, category, largestItem, itemCount
 └─ createdAt
```

## Purposes & relationships

| Model | Purpose | Key relationships |
|---|---|---|
| `User` | Account identity. Two auth fields (`email`, `passwordHash`) added by the explicit sign-in decision; they are nullable so pre-existing demo rows stay valid. | owns `Receipt` rows |
| `Receipt` | The accepted file's metadata. Holds only a storage **key** — the binary lives in the storage driver. | `userId → User`; `job → Job` |
| `Job` | The unit of background work. Its `status` drives the whole UI. | `receipt → Receipt`, `attempts → JobAttempt`, `extractionResult → ExtractionResult` |
| `JobAttempt` | One AI attempt = one row, preserving a complete processing/retry history — the evidence the whole design exists to produce. | `job → Job` |
| `ExtractionResult` | Role 1's **validated** output. Written only after the response passes the Zod gate. | `job → Job`, `summary → Summary` |
| `Summary` | Role 2's validated output, stored idempotently (max one per result). | `extractionResult → ExtractionResult` |

## Why the key, not the file

Only `Receipt.storageKey` is stored because uploaded binaries have no business in relational tables: they bloat backups, slow queries, and mix object blobs with structured rows. Files live in the storage abstraction (`local`/`s3`), and every downstream consumer — the worker, the summarizer — fetches by key through `StorageDriver.read()`. This separation is what makes swapping `STORAGE_DRIVER=local` → `s3` a config change rather than an architecture change.

# 5. The Concepts

Each entry: **what it is → why it matters here → how VoucherSense implements it.**

**1. API endpoint.** A URL the frontend talks to. The whole slice is driven by a small set of typed JSON routes (`/api/auth/register`, `/api/auth/login`, `/api/session`, `/api/receipts/batch`, `/api/jobs`, `/api/jobs/:id`, `/api/jobs/:id/result`, `/api/jobs/:id/retry`, `/api/results/:id/summarize`, `/api/results/:id/summary`). Every route is authenticated and ownership-checked.

**2. Official SDK vs raw HTTP.** Using `@google/genai` instead of hand-rolled fetch calls means the SDK handles auth, model routing, streaming/generation options, and schema payloads for us. VoucherSense wraps the SDK in exactly one module (`lib/ai/geminiClient.ts`) so no other code can drift into calling the provider differently.

**3. System prompts vs user prompts.** The system prompt sets the model's role and rules (fixed, per-role files: `extractorPrompt.ts`, `analystPrompt.ts`); the user-content part carries the task-specific input (the image, or the validated extraction JSON). This separation keeps role rules stable while the payload changes per call.

**4. Model parameters.** Tunables sent with each call: `temperature` (0 — extraction should be deterministic, not creative), `maxOutputTokens` (2000 — headroom for 40-item receipts, from PRD v2) and the enforced timeout. All live in `config/index.ts` and are env-overridable.

**5. Structured output.** Instead of free text, each call requests JSON via `responseMimeType: "application/json"` plus a Gemini-native `responseSchema` (translated from the PRD JSON schemas by `jsonSchemaToGeminiSchema`). This makes the model's contract machine-readable.

**6. Schema validation.** The strict contract that turns "the API succeeded" into "the response is well-formed". Two Zod mirrors (`lib/validation/extraction.ts`, `lib/validation/summary.ts`) re-check every field the model returns — the (summary/extraction) row is only written if the Zod gate passes.

**7. Validation failure.** A response that fails Zod is not a success and is not silently ignored. It becomes a `JobAttempt` with outcome `invalid_schema` (plus the specific issue in `validationError`) and the retry prompt gets the exact error.

**8. Background jobs.** Uploads must return instantly; AI work can take 30+ seconds. So each accepted file creates a `Job`, and a worker processes it out-of-band. The `Job` row is the single source of truth the UI polls.

**9. Worker.** A long-running Node process (`worker/index.ts`) with `WORKER_CONCURRENCY` independent loops. Each cycle: reap stale jobs → claim one → process it. It is deliberately separate from the Next.js app so AI work survives browser sessions.

**10. PostgreSQL queue/concurrency control.** The database itself is the queue. No Redis/BullMQ — the process polls and rows carry status. Concurrency is capped twice: by the worker loop count *and* by a global in-process AI semaphore in `geminiClient.ts` that spans both roles.

**11. `SELECT … FOR UPDATE SKIP LOCKED`.** The atomic claim: an `UPDATE … WHERE id = (SELECT … FOR UPDATE SKIP LOCKED LIMIT 1)` flips the oldest `pending` job to `processing` while skipping rows another worker is already locked on. This guarantees two loops can never pick the same job.

**12. Stale job recovery.** If a worker crashes mid-call, a job would sit in `processing` forever. The reaper (every poll cycle, before claiming) reclaims jobs older than `STALE_JOB_TIMEOUT_MS` — back to `pending` if attempts remain, otherwise `failed` with an honest message.

**13. Retry attempts.** Bounded retries with feedback: truncation and invalid-schema responses are retried up to `AI_MAX_RETRIES` times, each retry carrying the previous error. Timeouts and provider errors are terminal (PRD §4.2). Every attempt is a `JobAttempt` row; retry numbering continues across cycles so history stays readable.

**14. Rate limiting as cost control.** AI calls cost money and provider quota. Two independent per-user buckets (upload 10/min, summarize 20/min) bound how fast a single user can burn tokens; a rejection is an explicit 429.

**15. Object storage vs database storage.** Files belong in an object store (`local` disk or S3), not as BLOBs in Postgres. VoucherSense persists only a `storageKey` and treats it as an opaque handle.

**16. Storage abstraction.** A `StorageDriver` interface (`save(key)`, `read(key)`) with `local` and `s3` implementations chosen by `STORAGE_DRIVER`. Application code never touches an FS path or constructs S3 URLs; it only ever asks the driver "get this key".

**17. AI timeout.** Every call runs under an `AbortController` timer set to `AI_TIMEOUT_MS`. A slow provider aborts the call and records outcome `timeout` — there are no unbounded waits holding a worker slot.

**18. AI retry.** The bounded, context-aware retry loop (see #13). It exists because LLMs occasionally emit malformed or truncated JSON; one well-crafted retry usually fixes it, and the prompt discipline (never identical prompts) prevents the model from repeating the same mistake.

**19. AI failure handling.** Errors are normalised into one of four outcomes — `ok`, `truncated`, `timeout`, `provider_error` — so every caller classifies failure identically: truncation detours to a retry before parsing; provider errors are terminal, logged server-side for diagnosis, and surfaced to the user only as a safe, generic message (never provider internals).

**20. Cost model and configurable caps.** Budget knobs, all env-driven: `MAX_UPLOAD_BYTES`, `MAX_FILES_PER_BATCH`, the 40-item cap, `AI_MAX_OUTPUT_TOKENS`, rate-limit buckets, `WORKER_CONCURRENCY`. Each bound stops one category of runaway cost (huge uploads, giant batches, pathological responses, scripted clients, parallel calls).

**21. Authentication.** Account ownership. Registration requires a well-formed email and a `minPasswordLength` (8) password, hashes it with scrypt (unique 16-byte salt, constant-time compare, stored as `scrypt$salt$hash`), rejects duplicate emails, and issues nothing until login. The scope is deliberately minimal (no email verification, reset, social, roles).

**22. Session management.** State shared across requests via a signed cookie (`vs_session`). HMAC-SHA256 signature prevents forgery; `httpOnly` + `SameSite=Lax` (+ `Secure` in production) harden it; the token records `iat` and is rejected past `SESSION_MAX_AGE_SECONDS`. Without `SESSION_SECRET`, a random ephemeral secret is used in dev (sessions don't survive restarts).

**23. Ownership authorization.** "You may not read someone else's data." Every resource route resolves the URL id → job → receipt → `userId` and compares it with the session's user id; a mismatch is a 403. Authorization is always derived from the server-verified session, never from client-supplied ids.

# 6. What Went Wrong

Real problems encountered during implementation and verification. Each is supported by the repository or by confirmed testing.

## 1. The 30-second AI timeout was too tight for local Gemini latency

- **What happened:** background jobs failed with "The AI provider did not respond in time." (outcome `timeout`) immediately after claim.
- **Why:** a single Role 1 extraction call measured ~31.6 s on this machine/network against the documented 30 s default — the local free-tier/slow-network latency exceeds the default budget.
- **Detected:** worker log (`[processJob] job … failed: The AI provider did not respond in time.`) and a direct instrumented call that timed the real latency.
- **Fixed:** `.env` override `AI_TIMEOUT_MS=90000` and, to honour the config's own "2× the AI timeout" rule, `STALE_JOB_TIMEOUT_MS=180000`. After that, extraction completed (`done`) reliably.
- **Permanent or local tuning?** **Local tuning.** Code defaults and `.env.example` still say 30 s / 60 s.
- **Open decision:** the right value depends on network conditions and, critically, the deployment platform's function/request timeout (PRD §7.2 requires `AI_TIMEOUT_MS × (maxRetries + 1)` to fit under it and §12 item 1). Not resolved.

## 2. A 16-hour-old worker failed new jobs with "Processing failed unexpectedly."

- **What happened:** a fresh upload landed in `failed` with a generic message and no `JobAttempt` row.
- **Why:** a worker process had been running the pre-restart code for ~16 hours while the database/codebase moved on; it crashed on new work it no longer understood.
- **Detected:** DB inspection of the job row (failed, attemptCount 0, no attempts).
- **Fixed:** killed the stale process and restarted the worker from current code; the failed job was retried through the retry endpoint and processed cleanly.
- **Permanent or local tuning?** An operational fix — **restart workers whenever code or schema changes.** No code change was needed.

## 3. Duplicate `attemptNumber` rows in the job-attempt history

- **What happened:** older jobs showed multiple `JobAttempt` rows numbered `1` for the same job.
- **Why:** the retry route reset `attemptCount` to `0` when re-enqueuing a failed job, so the next processing cycle re-numbered its attempts from 1 — duplicating numbers and muddying the audit trail the design exists to produce.
- **Detected:** DB inspection of attempt rows for previously processed jobs.
- **Fixed:** the retry route now continues from the highest recorded attempt instead of resetting to 0. Verified post-fix: a bad-model run recorded `attempt 1 provider_error`, and after a successful retry the history read `1 provider_error → 2 valid`.
- **Permanent:** yes — a code change kept in the repository.

## 4. Transient Gemini 503 ("high demand") during a summary call

- **What happened:** a "Summarise expenses" call returned "The AI provider returned an error." and the `Summary` was recorded as `failed`.
- **Why:** the provider answered `503 UNAVAILABLE — This model is currently experiencing high demand` (seen in the server log). Transient provider-side capacity, not an app bug.
- **Detected:** server log (`[ai] provider call failed: … 503 …`) plus the honest `Summary.status = failed` row; the UI showed the failed state rather than inventing content.
- **Fixed:** re-attempted on a fresh result after the spike passed — the successful summary rendered in the UI. The failed summary remains honestly recorded.
- **Permanent or local tuning?** Provider spikes are external. **Open decision to flag:** per strict AGENTS.md rule 13, a `Summary` row, once created, is never re-triggered — so a failed summary on a given result stays failed. If retrying failed summaries is desired, the idempotency rule (rule 13) would need to be reopened.

## 5. Dev-mode hydration stalled when the app was reached via 127.0.0.1

- **What happened:** in `next dev`, pages rendered HTML but React never hydrated — no errors, no failed requests.
- **Why:** Next.js 16.2+ dev-HMR authentication is host-scoped. Loading via `http://127.0.0.1:3000` makes the dev server answer the HMR WebSocket with a bare `Unauthorized`, which stalls hydration. Production builds are unaffected.
- **Detected:** A minimal probe page hydrated fine via `localhost` but not via the IP, isolating the cause.
- **Fixed:** document/use `http://localhost:3000` for dev access (noted in [Section 2](#2-how-to-run-it)). No code change.
- **Permanent:** an environment/tooling constraint of Next.js dev mode, not an app defect.

## 6. Authentication was documented as out of scope while the requirement said otherwise

- **What happened:** early AGENTS.md/PRD text described "no accounts beyond a single seeded demo user" and listed the authentication system as out of scope, while the confirmed requirement for this slice is a minimal Register → Login → Upload → Jobs → Results flow with real accounts.
- **Why:** the auth requirement post-dated (or contradicted) the PRD's original v2 scope line.
- **Detected:** during planning, when the confirmed requirement was compared against AGENTS.md §3 rule 16.
- **Fixed:** AGENTS.md now states a minimal auth system **is in scope** (register, login, secure hashing, sessions, logout, route protection, ownership checks) and lists only the advanced features (email verification, password reset, social login, profile management, account settings, advanced account features) as out of scope. The app, database, and AI architecture already matched the confirmed requirement.
- **Permanent:** yes (documentation fix).

# 7. What This Slice Does Not Handle

Confirmed out-of-scope items (aligned with AGENTS.md §3, rule 16, and PRD §11):

- **No editing of extracted fields.** Extracted data is shown as validated output; there is no in-app correction workflow.
- **No export.** No CSV/PDF export of expenses or summaries.
- **No sharing.** No team/partner collaboration, shared batches, or public links.
- **No invoicing.** No generation or management of invoices.
- **No budgeting / dashboards.** No spend analytics, budgeting, charts, or period rollups beyond the per-receipt summary.
- **No multi-page receipt workflow.** A multi-page receipt is not handled as such; each uploaded file is processed as one receipt. Single images and PDFs are the supported input classes.
- **No multi-currency accounting.** Currency is captured (ISO 4217) but there is no conversion, currency-level totals, or multi-currency arithmetic.
- **No advanced account management.** No email verification, password reset, social login, profile management, or account settings.
- **No additional AI roles.** Only the two roles — Extractor and Analyst — are in scope.
- **No retention / cleanup tooling.** No file-expiry, deletion, or storage-cleanup jobs (deleting a stored object is not even an operation the storage interface defines).
- **No full accounting platform.** This is a focused engineering slice: one flow, done properly.

# 8. If I Built This Again

Honest, practical reflection — not a wishlist.

**Timeout and retry design would be latency-driven from day one.** The single biggest runtime lesson was that a "reasonable" 30 s default is easy to pick and easy to get wrong. I would start from *measured* provider latency on the actual target network, then set `AI_TIMEOUT_MS` from data (with headroom) and derive `STALE_JOB_TIMEOUT_MS` automatically (2×) rather than as a second manual guess. I would also record per-attempt latency in `JobAttempt` — the schema currently stores raw responses and validation errors but not durations, which would make capacity planning much easier.

**The queue is the right size right now; scaling it is a deliberate step, not a rewrite.** Postgres `SKIP LOCKED` polling is perfect for a single-node MVP and buys genuine concurrency safety with almost no infrastructure. When (and only when) a real deployment needs scale — many workers, high job throughput, fan-out — I would move to a purpose-built queue (BullMQ/Redis or a managed queue), but I would keep the `Job`/`JobAttempt`/status model as the durable source of truth so the migration is additive.

**Rate-limit storage would become external the moment a second instance exists.** In-memory token buckets are correct for one process and trivially wrong for two — each instance would have its own independent budget and 2× the effective limit. A shared store (Redis or a Postgres-backed counter) should be chosen as part of the deployment decision, not after it.

**Better observability.** The app logs structured, useful lines (claim, per-job outcome, provider errors), but I would add: per-attempt timing, provider status/outcome counters, job-latency histograms, and correlation ids across upload→job→result. "A job failed" is knowable today; "why, how often, and how fast across the fleet" would need telemetry.

**Stronger automated integration testing.** Unit tests (validation, rate limiting, concurrency, file checks, auth primitives — 45 tests) are solid, but the live E2E around them (real browser uploads, real worker cycles, real Gemini calls) was scripted and manually driven. I would build a repeatable integration harness against the real stack — including a disposable worker, a real Postgres, and a mocked provider for deterministic failure paths — so layout, hydration, and full-job lifecycle regressions are caught automatically instead of by inspection.

**Storage and deployment need a real production decision.** Today's local driver is a correct dev stand-in; an S3-compatible object store and the S3 driver already exist behind the same interface, so moving is configuration. The genuinely unresolved production questions are: the deployment target (which governs the worker's persistent-process requirement and whether Role 2's synchronous design fits inside the platform's function timeout), the exact Gemini model/account, and the rate-limit store. Those three PRD §12 decisions would be locked before anyone called this deployable.

**Provider latency should drive timeout *and* the analyst's execution model.** Role 2 is a deliberate synchronous exception on the assumption that a small JSON payload answers fast. With the provider occasionally slow or "high demand" (see [Section 6](#6-what-went-wrong)), that assumption is worth re-checking against the chosen platform: if the maths (`AI_TIMEOUT_MS × (maxRetries + 1)`) no longer fits under the platform ceiling, Role 2 should move onto the same job queue as Role 1 rather than inventing a separate path.

None of this changes the core shape — validated structured output through a durable queue, honest failure records, hard caps, and per-user ownership are the parts of this slice I would keep as-is.
